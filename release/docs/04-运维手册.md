# DMS 文档管理系统 —— 运维手册

> 版本：1.0.0　　目标系统：Debian 13 / amd64
> 面向日常值班与故障处理：备份恢复、监控、日志、常见故障、升级回滚、安全加固。

## 1. 日常检查清单（建议每天 5 分钟）

```bash
# 一键自检（服务/端口/库/对象存储/接口/前端/定时任务，约 40 项）
/root/dms-release-1.0.0/deploy/verify-deploy.sh

# 关键指标
systemctl is-active dms-app minio nginx postgresql redis-server
df -h /                      # 磁盘（对象存储与备份都在系统盘时尤其要看）
free -h                      # 内存
du -sh /var/dms/tus          # 上传临时文件（异常增长说明有大量中断上传）
du -sh /opt/dms/backup       # 备份占用
tail -50 /opt/dms/logs/dms.log
```

页面上的「系统信息」页（`/system/info`）把这些都做成了可视化：**业务数据量在最前面**，
后面依次是服务器（发行版/内核/CPU 型号/1-5-15 分钟负载/Swap/开机时长/内存）、
应用（JVM 堆/元空间/线程/类加载/GC 次数与耗时/启动参数/时区语言）、磁盘、
数据库、MinIO（配置 + 运行状态）、Redis。它是最省事的巡检入口。

## 2. 备份与恢复

### 2.1 自动备份

`dms-backup.timer` 每天 **02:30** 执行 `/opt/dms/backup/backup.sh`，备份三样东西：

| 内容 | 位置 | 说明 |
| --- | --- | --- |
| 数据库 | `sets/<时间戳>/db.dump` | `pg_dump -Fc`，可选择性恢复 |
| 对象存储 | `sets/<时间戳>/minio/dms-files/` | `mc mirror` 成普通文件，恢复时反向 mirror |
| 配置与元信息 | `config/`、`minio.env`、`objects.txt`、`db-counts.txt` | 含行数快照，恢复后逐项核对 |

```bash
systemctl list-timers dms-backup.timer        # 看下次执行时间
tail -50 /opt/dms/backup/backup.log           # 看备份日志
ls -lh /opt/dms/backup/sets | tail            # 看备份集
```

**默认只备份到本机**：这能防误删、误操作、程序 bug，但**防不了磁盘损坏或整机故障**。
生产环境务必设置异机备份：

```bash
# /etc/systemd/system/dms-backup.service 里加一行 Environment=
Environment=DMS_BACKUP_REMOTE=nas:/volume1/dms-backup
# 或直接改 /etc/default/dms-backup 后 systemctl daemon-reload
# 需要先配置免密 SSH（root@本机 → NAS）并用 rsync 试通
```

保留策略：`DMS_BACKUP_KEEP_DAYS`（默认 30 天）。磁盘紧张时调小，但**不要取消异机备份**。

### 2.2 恢复

```bash
cd /opt/dms/backup
./restore.sh --list                      # 列出可用备份集
./restore.sh --drill <备份集>            # ★ 恢复演练：恢复到临时库 + 临时桶，逐项核对行数
./restore.sh --db <备份集>               # 只恢复数据库
./restore.sh --minio <备份集>            # 只恢复对象
./restore.sh --all <备份集>              # 全量恢复（会覆盖当前库与桶，需二次确认）
```

**建议每季度做一次 `--drill`**：它是唯一能在"还没出事"的时候证明备份真的能用的手段。
演练会创建临时库与临时桶，跑完自动清理，不影响生产数据。

恢复后核对要点（脚本会打印对比）：

* `doc_file` / `doc_folder` 行数（在用的与含回收站的都要对）；
* `doc_folder_permission` / `doc_file_permission` 授权条数；
* MinIO `files/` 对象数应与 `doc_file` 在用行数一致（对不上说明备份不完整）。

## 3. 日志

| 日志 | 位置 | 用途 |
| --- | --- | --- |
| 应用日志 | `/opt/dms/logs/dms.log`（按天轮转，保留 14 天，压缩） | 业务与异常排查，**首选** |
| JVM 标准输出 | `/opt/dms/logs/stdout.log` | 启动过程、框架日志 |
| JVM 标准错误 | `/opt/dms/logs/stderr.log` | **启动失败先看这里** |
| systemd journal | `journalctl -u dms-app` | 服务生命周期、被 systemd 杀的记录 |
| nginx 访问/错误 | `/var/log/nginx/dms-{access,error}.log` | 访问与反代问题 |
| 备份日志 | `/opt/dms/backup/backup.log` | 备份结果 |
| MinIO | `journalctl -u minio` | 对象存储异常 |
| OnlyOffice | `docker logs onlyoffice` | 预览/编辑问题 |

日志容量控制：`/etc/logrotate.d/dms` 管应用日志；`/etc/systemd/journald.conf.d/dms-limits.conf`
把 journald 限制在 512MB / 保留 30 天（默认不限制，长期运行会把 `/var/log/journal` 撑大）。

```bash
# 排查典型问题时
grep -i "ERROR\|Exception" /opt/dms/logs/dms.log | tail -30
journalctl -u dms-app --since "30 min ago"
awk '{print $NF}' /var/log/nginx/dms-access.log | sort | uniq -c | sort -rn | head   # 状态码分布
```

## 4. 常见故障处理

### 4.1 上传大文件失败

1. nginx：确认 `client_max_body_size 0;`（模板里是 0 = 不限制）。
2. 应用：`dms.upload.max-size`（默认 10737418240 = 10GB）与
   `spring.servlet.multipart.max-file-size`。
3. 磁盘：`df -h /`、`du -sh /var/dms/tus`、`du -sh /opt/minio/data`。
4. tus 临时文件堆积：默认 48 小时清理（`TusCleanupJob` 每天 04:20），
   紧急时可手工清理 48 小时前的目录：

```bash
find /var/dms/tus -mindepth 1 -maxdepth 1 -type d -mtime +2 -exec rm -rf {} +
```

### 4.2 图片/视频不显示

* 直链是**短期签名令牌**（默认 120 分钟）。页面开着不动超过这个时间，图片会失效，
  刷新页面即可。
* 检查 `/api/doc/files/{id}/media` 的返回；若 401/403，看该用户对该文件的预览权限。
* `security.excludes` 必须包含 `/api/doc/media/**`，否则浏览器原生请求会被判未登录。

### 4.3 文档预览白屏 / 方框

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 白屏、iframe 里是 DMS 页面 | nginx 里 OnlyOffice 的反代规则被后端正则抢先匹配 | 确认 `location ~ ^/(?:\d+\.\d+\.\d+[-.]\w+/|(?:web-apps|sdkjs|...)/?)` 排在 `location ~ ^/(auth|system|...)/` **之前** |
| 中文显示为方框 | OnlyOffice 容器没装中文字体 | 重新执行 `install-onlyoffice.sh`（会复制 `/usr/share/fonts/**/noto` 到 `/opt/onlyoffice/fonts`） |
| 提示"下载失败/令牌校验不通过" | JWT 开关与密钥不一致 | 确认容器 `JWT_ENABLED=false`，或两处 secret 一致 |
| 完全打不开 | 容器没起 | `docker ps -a \| grep onlyoffice`、`docker logs onlyoffice` |

不想依赖 OnlyOffice 时可临时关掉（系统参数 `dms.onlyoffice.enabled=false`），
Office/PDF 预览会回落为「服务端转换的 PDF + pdf.js」。

### 4.4 上传站点图标报 `Read-only file system`

systemd 用了 `ProtectSystem=strict`，只有 `ReadWritePaths` 白名单内的目录可写。
站点资源目录必须同时满足：**目录存在且属主是 `dms`** + **在白名单里**。

```bash
grep ReadWritePaths /etc/systemd/system/dms-app.service
mkdir -p /opt/dms/site-assets && chown -R dms:dms /opt/dms/site-assets
# 若缺这个目录：编辑单元 → 加进 ReadWritePaths → systemctl daemon-reload → restart dms-app
```

### 4.5 权限"看起来不对"

排查顺序：

1. 「系统信息」页 → 业务数据量 → 授权条数是否符合预期；
2. 该资源的「权限设置」弹窗里看**实际生效**的授权（含继承来的）；
3. 记住判定规则：多主体**取并集**、「禁止访问」**一票否决**且向下继承、
   文档区所有者与内置超管不受限；
4. 授权有到期时间（`expires_at`），过期即失效；
5. 角色改过权限后，**在线用户会被踢下线**，需要重新登录才拿到新权限串。

### 4.5b 除了图片和视频，所有文档都打不开（弹「错误 / 下载失败」）

**现象**：打开任何 PDF/Word/Excel/CAD 都弹出「错误：下载失败」；
编辑器界面本身能加载、甚至能显示文件名与页数；但**图片、视频一切正常**。

**根因**：OnlyOffice 给缓存地址（`/cache/files/...`）签名用的密钥与 nginx 校验用的密钥不一致。

* 文档服务签名用 `local.json` → `storage.fs.secretString`
* nginx 校验用 `/etc/onlyoffice/documentserver/nginx/ds.conf` 里的 `$secure_link_secret`
* 后者由容器启动时的环境变量 `SECURE_LINK_SECRET` 决定，**没给就是每次重启随机生成**

只要两者不同，签名校验必然失败 → 403 → 编辑器拿不到文档本体 → 「下载失败」。
图片/视频不走 OnlyOffice，所以不受影响——**"只有文档打不开"正是这个故障的指纹**。

**为什么容器一重建就坏**：`SECURE_LINK_SECRET` 不是持久化的，重建容器时忘了带这个环境变量，
nginx 就拿到了新随机值，而 `local.json` 里还是旧密钥 → 从那一刻起所有文档都打不开。

**排查（三条命令）**：

```bash
# 1) 三处取值是否一致
python3 -c "import json;print(json.load(open('/opt/onlyoffice/local.json'))['storage']['fs']['secretString'])"
docker exec onlyoffice grep -o 'secure_link_secret [A-Za-z0-9]*' /etc/onlyoffice/documentserver/nginx/ds.conf
docker exec onlyoffice printenv SECURE_LINK_SECRET

# 2) 文档服务能否拉到文档（应 200）
docker exec onlyoffice curl -s -o /dev/null -w '%{http_code}\n' "<应用给编辑器的 document.url>"

# 3) 缓存地址的实际状态码（403 = 签名校验不过）
grep '/cache/files' /var/log/nginx/dms-access.log | tail -5 | awk '{print $9, $7}'
```

**修复**：让三处取同一个值（推荐用 `local.json` 里已有的 `storage.fs.secretString`）：

```bash
SECRET=$(python3 -c "import json;print(json.load(open('/opt/onlyoffice/local.json'))['storage']['fs']['secretString'])")
docker rm -f onlyoffice
docker run -d --name onlyoffice --restart always -p 127.0.0.1:8081:80 \
  -e JWT_ENABLED=false -e SECURE_LINK_SECRET="${SECRET}" \
  -v /opt/onlyoffice/local.json:/etc/onlyoffice/documentserver/local.json:ro \
  -v /opt/onlyoffice/fonts:/usr/share/fonts/truetype/custom:ro \
  -v /opt/onlyoffice/fonts-alias.xml:/etc/fonts/conf.d/99-dms-cjk-alias.conf:ro \
  onlyoffice/documentserver:latest
# 校验：容器内 nginx 的 $secure_link_secret 应等于 ${SECRET}
```

`deploy/install-onlyoffice.sh` 会把密钥固定保存在 `/opt/onlyoffice/.secure_link_secret` 并在重建时复用，
所以**用它部署/重建不会踩这个坑**；手工 `docker run` 时务必带上 `SECURE_LINK_SECRET`。

另一类同类现象：nginx 的反代路径清单里**漏了 `downloadfile`**，`POST /downloadfile/<key>`
会落到 SPA 规则返回 405，文档同样取不到。`deploy/verify-deploy.sh` 会同时检查
`downloadfile / savefile / converter / upload` 四条路径是否已代理。

### 4.6 应用起不来

```bash
tail -50 /opt/dms/logs/stderr.log
# 三种高频原因：
#  a) 配置文件名与 profile 不匹配（外部配置必须叫 application-prod.yml，systemd 里传 --spring.profiles.active=prod）
#  b) 数据库口令不一致（compare /root/.dms-credentials 与 /opt/dms/config/application-prod.yml）
#  c) 8080 被占：ss -ltnp | grep 8080
```

## 5. 升级与回滚

```bash
tar xzf dms-release-1.0.1-core.tar.gz && cd dms-release-1.0.1
./deploy/upgrade.sh /root/dms-release-1.0.1
```

升级脚本的顺序是：备份 → 停应用 → 替换 jar/前端 → 应用新迁移 → 启动 →
自检 → 通过则收尾、不通过**自动回滚**（代码与配置），旧版本内容留在
`/opt/dms/rollback/<时间戳>/`。

数据库迁移只增不改，回滚代码一般不需要回滚库。若某次升级包含结构变更，
升级脚本会在输出里提示，回滚前请先看提示。

## 6. 安全加固现状与建议

已做的（部署即生效）：

| 项 | 状态 |
| --- | --- |
| 对外端口 | 只有 22（限内网网段）与 80；8080/8081/9000/9001/5432/6379 全部只监听 127.0.0.1 |
| 应用运行身份 | 专用系统账号 `dms`（无登录 shell） |
| systemd 沙箱 | `NoNewPrivileges`、`ProtectSystem=strict`、`ProtectHome`、`ProtectKernel*`、`RestrictSUIDSGID`、`LockPersonality` + 可写路径白名单 |
| 口令 | 数据库/Redis/JWT/MinIO/管理员全部为随机强口令，存 `/root/.dms-credentials`（600） |
| 对象存储 | 应用只用最小权限账号（限单桶），root 仅用于控制台 |
| 接口加密与验证码 | 内网部署默认关闭（`api-decrypt.enabled=false`、`captcha.enable=false`） |
| 演示账号 | 部署时自动停用框架自带的 `test`/`test1`（口令是公开的） |
| 上传防护 | 单文件上限、类型识别、tus 临时目录定期清理 |

建议加固（按优先级）：

1. **改管理员口令**并删除不再使用的账号；
2. 数据库与 Redis 口令**定期轮换**（改配置文件 → 重启应用；改 Redis 需同步改配置）；
3. 若走域名/HTTPS：见《03-部署手册.md》第 5 节；
4. 开启 ufw 限制 22 端口的来源网段；
5. 定期检查 `/root/.dms-credentials` 的权限（应为 600）；
6. 审计日志按需导出归档（清除日志只有内置超管能做，且会留痕）。

## 7. 容量规划

| 资源 | 现状 | 建议 |
| --- | --- | --- |
| 应用内存 | 堆默认物理内存 1/4（上限 4G） | 8GB 内存机器够用；上传大文件并发高时优先加内存 |
| 数据库 | 空库约 70MB | 十万级文档约几百 MB，顺带做备份 |
| 对象存储 | 按文档量 | TB 级也没问题（单机单盘）；注意与系统盘分离 |
| 上传临时目录 | 峰值≈并发上传体积 | 建议至少 20GB 可用 |
| 备份 | 每份≈库+对象全量 | 保留 30 天，务必异机；量大时改为增量策略 |
| LibreOffice 转换 | 单进程串行 | 大量并发预览时 CPU 是瓶颈（8 核足够几十人用） |

## 8. 常用运维命令速查

```bash
# 服务
systemctl {status,restart,stop,start} dms-app
systemctl {status,restart} minio nginx postgresql redis-server
systemctl list-timers 'dms-*'

# 数据库
runuser -u postgres -- psql -d dms -c "\dt"                       # 列表
runuser -u postgres -- psql -d dms -c "select count(*) from doc_file where deleted_at is null"
runuser -u postgres -- psql -d dms -c "select version from dms_schema_migrations order by version"
runuser -u postgres -- pg_dump -Fc dms > /tmp/dms-$(date +%F).dump

# 对象存储
mc ls --recursive local/dms-files | wc -l                        # 对象数
mc du local/dms-files                                            # 占用
mc admin user list local; mc admin policy list local
# 清理"库里已无引用"的孤儿对象（默认只报告，不会误删）
python3 /path/to/tools/minio_sweep_orphans.py
python3 /path/to/tools/minio_sweep_orphans.py --delete

# 应用
ss -ltnp | grep 8080
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1/       # 前端
curl -s http://127.0.0.1:8080/auth/login -X POST -H 'Content-Type: application/json' \
  -H 'clientid: e5cd7e4891bf95d1d19206ce24a7b32e' \
  -d '{"username":"admin","password":"<口令>","clientId":"e5cd7e4891bf95d1d19206ce24a7b32e","grantType":"password"}'
```

> 注意：`/api/doc/system/info`、「系统信息」页、审计日志清除等能力有权限限制，
> 用普通账号调用会返回 403 —— 这是设计如此，不是故障。
